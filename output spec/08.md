# Phase 08 Implementation Record

## Phase

Phase 6: Asynchronous Queue System

## Implemented

- Added required job types:
  - `SOURCE_TRANSACTION_PROCESSING`
  - `TRADE_DETECTION`
  - `COPY_TRADE_CREATION`
- Added migration `004_queue_jobs.sql` with durable `queue_jobs` and `queue_dead_letters` tables.
- Added unique idempotency keys so duplicate enqueue requests return the existing job.
- Added job IDs, payloads, status, attempt counters, maximum attempts, scheduling timestamps, leases, worker ownership, and last-error fields.
- Added PostgreSQL job claiming with `FOR UPDATE SKIP LOCKED` for safe multi-worker concurrency.
- Added processing leases so jobs abandoned by a crashed worker can be claimed after lease expiry.
- Added acknowledgement guarded by job ID and worker ID.
- Added exponential retry delay with a maximum delay.
- Added dead-letter persistence after the maximum attempt count.
- Added an in-memory queue implementation for deterministic unit tests.
- Added a bounded-concurrency worker runtime.
- Added graceful worker shutdown that stops claiming and waits for active work to finish.
- Added a source-transaction adapter that converts listener events into idempotent `SOURCE_TRANSACTION_PROCESSING` jobs.
- Kept transaction detection and copy-trade creation as explicit handler types without implementing their business logic.

## Queue Flow

```text
Blockchain Listener
  -> SourceTransactionQueue adapter
  -> JobQueue.enqueue(SOURCE_TRANSACTION_PROCESSING)
  -> Queue Worker claim with lease
  -> Registered handler
  -> acknowledge, retry, or dead letter
```

The durable queue uses PostgreSQL as the persistence boundary. Multiple workers can claim different jobs concurrently, while the lease and worker ID prevent ordinary duplicate processing. A crashed worker's expired lease makes its job claimable again.
